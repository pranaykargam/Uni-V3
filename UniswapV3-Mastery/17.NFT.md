# 🦄 Uniswap V3 Milestone 6 — NFT Position Manager

## 📌 Index: Quick Reminders



### 🟦 NFT Fundamentals & Architecture

1. **`NFT position`** — A unique token represents the right to manage a specific liquidity position.  
2. **`ERC-721 ownership`** — `ownerOf(tokenId)` identifies the holder; approvals can let others manage the NFT’s position.  
3. **`Position Manager`** — Connects NFT ownership to Uniswap pool positions; the manager is the pool’s position owner.  
4. **`Position mapping`** — `positions[tokenId]` records the pool and tick range needed to locate the underlying position.  

### 🟩 NFT Position Lifecycle

5. **`Mint`** — Adds liquidity, creates an NFT, and links its ID to the position.  
6. **`Add liquidity`** — Increases liquidity associated with an existing NFT.  
7. **`Remove liquidity`** — Decreases pool liquidity and records tokens owed for collection.  
8. **`Collect`** — Transfers tokens owed from the pool; it is separate from removing liquidity.  
9. **`Burn`** — Destroys the NFT only after liquidity and owed tokens are cleared.  
10. **`NFT transfer`** — Changes the ERC-721 holder; the manager remains the pool-level owner.  

### 🟨 Metadata & Internal Accounting

11. **`Renderer and ``tokenURI``** — Builds JSON/SVG metadata; it does not prove the position’s actual balances.  
12. **`Shared core position risk`** — NFTs with the same manager, pool, and ticks may refer to one aggregated pool position.  

### 🟥 Smart Contract Audit & Security

13. **`Callbacks and external calls`** — Pool, token, and safe-transfer receiver calls can execute external code.  
14. **`Core audit invariant`** — Each NFT must only control its own accounted liquidity and fees.

## 🧠 Short Technical Notes

### 1. Ownership and Approvals

ERC-721 tracks the owner of each unique `tokenId`. A token-specific approval (`approve`) covers one NFT; `setApprovalForAll` covers the owner’s collection NFTs. In a position manager, an approved operator may be able to remove liquidity or collect tokens, so trace the authorization checks on every state-changing function.

### 2. Manager and Pool Accounting

The pool identifies a position by **owner + lower tick + upper tick**. When positions are created through a manager, the pool sees the **manager address** as owner. The NFT holder is tracked separately by ERC-721, and the manager uses its `tokenId` mapping to connect that holder’s NFT to pool and tick data.

### 3. Lifecycle

- **Mint:** Find the intended pool, add liquidity, mint an NFT, and store its pool and ticks. Check pool validation, tick rules, slippage minimums, callback behavior, and state consistency.
- **Add liquidity:** Use the stored pool and ticks to increase liquidity. Check token ID validity, authorization, payer, and minimum amounts.
- **Remove liquidity:** Reduce liquidity in the pool. Check authorization and ensure the amount removed is limited to that NFT’s recorded share.
- **Collect:** Withdraw tokens owed after fees accrue or liquidity is removed. Check who can collect and who receives the tokens.
- **Burn:** Clear the NFT only when liquidity and both token-owed balances are zero.
- **Transfer:** Changes the ERC-721 owner, not the pool’s owner. Confirm future management rights follow the new holder.

### 4. Per-NFT Accounting

The pool’s position key does **not** include the NFT ID. Two NFTs with the same manager, pool, and tick range can share the same core position. Therefore, the manager needs accounting that attributes liquidity and fees to each NFT; otherwise one NFT could withdraw or collect value attributed to another.

> **Invariant to check:** the sum of per-NFT liquidity should match the manager’s corresponding core liquidity, and each NFT should only remove or collect its own accounted share.

### 5. External Calls and Callbacks

Trace calls to pools, ERC-20 tokens, token metadata methods such as `symbol()`, and ERC-721 receiver hooks. Check state updates, authorization, reentrancy exposure, and whether failures can leave mappings and pool accounting inconsistent. An external call is a review point; assess whether it can actually violate an invariant.

### 6. Metadata and Renderer

`tokenURI()` may generate an SVG, embed it in JSON, and Base64-encode the result. Check that the token exists, output is valid, tick signs and values render correctly, and untrusted token symbols cannot break SVG/XML or JSON. Treat metadata as display output—not evidence of ownership, liquidity, or fees.

## 🔄 Combined Flow: User View and Uniswap V3 View

| Step | User / NFT Holder | Position Manager | Uniswap V3 Pool |
|:---:|---|---|---|
| **1. Mint** | Chooses pool, fee, tick range, amounts, and NFT recipient. | Validates inputs, adds liquidity, creates `tokenId`, and stores pool/tick data. | Adds liquidity to the position keyed by manager + tick range. |
| **2. Hold or Transfer** | Holds the NFT or transfers it; may approve an operator. | ERC-721 records the current owner and approvals. | Still sees the manager as the position owner. |
| **3. Add Liquidity** | Requests more liquidity for the NFT. | Checks the NFT and relevant permissions; maps its ID to pool/ticks. | Increases the manager-owned position for those ticks. |
| **4. Remove Liquidity** | Requests a decrease. | Checks permission and the NFT’s accounted liquidity. | Decreases liquidity and records amounts owed. |
| **5. Collect** | Requests owed tokens. | Applies authorization and recipient rules. | Sends collected tokens to the recipient specified by the manager. |
| **6. Burn** | Closes the empty position. | Confirms zero liquidity and no tokens owed, clears position data, then burns the NFT. | Has no remaining liquidity or owed amounts for that position. |

## ✅ Audit Pass Checklist

1. Trace every external function and its authorization.
2. Follow `tokenId → stored position → pool position key`.
3. Determine whether multiple NFTs can share that core key.
4. Verify per-NFT liquidity, fee, and owed-token accounting.
5. Check mint slippage and tick/pool validation.
6. Trace token recipients for removal and collection.
7. Review pool, token, and receiver callbacks for invariant-breaking reentrancy.
8. Confirm transfer changes control as intended.
9. Confirm burn cannot strand liquidity or owed tokens.
10. Treat `tokenURI()` as metadata, not financial proof.
