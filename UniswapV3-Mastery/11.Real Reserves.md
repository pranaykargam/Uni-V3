## 1. Reserves by Price Position

For a position with lower price `Pl`, upper price `Pu`, and current price `Pc`:

| Current price | Token X reserve | Token Y reserve |
|---|---|---|
| `Pc < Pl` | `L * (1/sqrt(Pl) - 1/sqrt(Pu))` | `0` |
| `Pl <= Pc <= Pu` | `L * (1/sqrt(Pc) - 1/sqrt(Pu))` | `L * (sqrt(Pc) - sqrt(Pl))` |
| `Pc > Pu` | `0` | `L * (sqrt(Pu) - sqrt(Pl))` |

- Below range: all token X.
- Inside range: both tokens.
- Above range: all token Y.
- At a boundary, one token reserve is zero.
- These are position-level amounts, not necessarily the pool’s total balances.

## 2. Reserves Between Two Prices

For `Pa < Pb` and liquidity `L`:

- If `Pc < Pa`: only token X is held between the prices.
- If `Pc > Pb`: only token Y is held between the prices.
- If `Pa <= Pc <= Pb`: token X is calculated from `Pc` to `Pb`, while token Y is calculated from `Pa` to `Pc`.

The relevant interval boundaries determine the token amounts.

## 3. Swap Connection

- `getAmount0Delta()` calculates the token X amount between two square-root prices.
- `getAmount1Delta()` calculates the token Y amount between two square-root prices.
- A swap may consume all liquidity in one price segment and reach a tick boundary.
- At that boundary, the swap can cross the tick and continue with a different active liquidity amount.
- These functions calculate movement between prices; they do not execute an entire swap by themselves.

## 4. Implementation Notes

- Uniswap V3 stores `sqrtPriceX96` in Q64.96 fixed-point format.
- `getAmount0Delta()` and `getAmount1Delta()` use `FullMath.mulDiv()` to avoid intermediate overflow.
- The `roundUp` flag controls whether the result rounds up or down.
- Rounding direction matters: swaps and liquidity accounting must not allow free value leakage through rounding.
- Check the actual implementation in [`SqrtPriceMath.sol`](https://github.com/Uniswap/v3-core/blob/main/contracts/libraries/SqrtPriceMath.sol), not only simplified formulas.

## 5. Auditor Checklist

- Are prices below, inside, and above the range handled correctly?
- Are lower and upper boundaries used in the correct order?
- Are token X and token Y calculations clearly separated?
- Is Q64.96 scaling handled consistently?
- Is integer division and rounding direction correct?
- Does the caller use the returned amount correctly for mint, burn, collect, or swap?
- Do tests cover boundary prices, zero liquidity, equal prices, and extreme inputs?
- Is active liquidity updated correctly when a swap crosses a tick?
