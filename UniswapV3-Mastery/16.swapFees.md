# Uniswap V3 — Swap Fees

## Core Idea

**Swap fees** are fees paid by traders when they swap tokens. These fees are distributed to **Liquidity Providers (LPs)** whose liquidity was active during the swap.

---
# PART-01👇🏻
## Important Terminology

### 1. Engaged / Active Range
A liquidity range is **engaged** when the current price is inside that range.

```text
100 ─────── 150 ─────── 200
             ↑
        Current Price

        ✅ Engaged
```

The liquidity can participate in swaps and earn fees.

### 2. Disengaged / Inactive Range
A range is **disengaged** when the current price is outside the range.

```text
100 ─────── 200 ─────── 250
                         ↑
                    Current Price

                    ❌ Disengaged
```

That liquidity does not earn fees from swaps occurring outside its range.

### 3. Tick
A **tick** is a price boundary.

When a swap moves the price across a tick, the active liquidity/ranges can change.

```text
Price moves → Tick crossed → Active range changes
```

### 4. Global Fee Counter
Uniswap V3 keeps:

```solidity
feeGrowthGlobal0X128
feeGrowthGlobal1X128
```

These track **total accumulated fees per unit of liquidity**.

Instead of updating every LP after every swap, Uniswap updates this global accounting.

### 5. Fees 


    (Global Fees)- (Fees below lower tick) - (Fees above upper(Fees INSIDE the position)

### 6. Pro Rata
**Pro rata** means **proportionally according to the amount of liquidity provided**.

Example:

```text
Total active liquidity = 1,000
Your liquidity         = 100

Your share = 10%
```

So you receive approximately 10% of the fees applicable to that active liquidity.

# Removing Liquidity — `burn()` & `collect()`

## 1. Liquidity vs Token0/Token1

- `liquidity` is **not a third token**.
- It is a mathematical representation of a position's liquidity.
- The actual token0/token1 amounts represented by that liquidity depend on:
  - current price
  - position's lower/upper tick range
  - liquidity amount

```text
token0 + token1
      +
price range
      +
current price
      ↓
liquidity value
```

The number such as `1000` is only an example.

---

## 2. What happens during a swap?

If my position is active:

```text
My liquidity → used by the pool for swaps
```

A trader can receive token1 from the pool even though LPs supplied the pool's assets.

```text
LP
 ↓
token0 + token1
 ↓
POOL
 ↓
Trader swaps
 ↓
Trader receives token
```

The trader does **not take my liquidity ownership**.

During a swap:

```text
Liquidity value     → normally stays the same
Token0/token1 mix   → can change
Fees earned         → increase
```

### Important

```text
SWAP
→ uses liquidity
→ does not remove liquidity

BURN
→ removes liquidity
```

---

# 3. Fee distribution

If multiple positions are active:

```text
You  = 1000 liquidity
LP B = 2000 liquidity

Total active liquidity = 3000
```

Fee share is proportional:

```text
You  = 1000 / 3000
LP B = 2000 / 3000
```

This ratio determines **fee share**, not liquidity reduction.

---

# 4. `burn()`

`burn()` is the opposite of `mint()`.

```text
mint
→ +liquidity

burn
→ -liquidity
```

```solidity
liquidityDelta = -(int128(amount));
```

`burn()`:

1. Removes liquidity from the position.
2. Calculates the token0/token1 amounts represented by the removed liquidity.
3. Updates fee/accounting information.
4. Adds the resulting amounts to `tokensOwed0` / `tokensOwed1`.

---

# 5. `_modifyPosition()`

Both `mint()` and `burn()` use:

```text
_modifyPosition()
```

```text
mint
 ↓
_modifyPosition(+liquidity)

burn
 ↓
_modifyPosition(-liquidity)
```

It handles common position logic such as:

- tick updates
- position updates
- liquidity changes
- token0/token1 amount calculation
- fee accounting

---

# 6. Liquidity → Token Amounts

When liquidity is burned, V3 calculates:

```text
removed liquidity
        +
current price
        +
position range
        ↓
current token0 amount
+
current token1 amount
```

The token amounts can change as the price changes even if the position's liquidity value has not changed.

---

# 7. `tokensOwed`

After burning:

```text
liquidity ↓
tokensOwed0 ↑
tokensOwed1 ↑
```

`tokensOwed` represents tokens that the position can withdraw.

```text
Position
├── liquidity
│   → active V3 liquidity
│
├── tokensOwed0
│   → withdrawable token0
│
└── tokensOwed1
    → withdrawable token1
```

Conceptually:

```text
tokensOwed
=
removed token amounts
+
accumulated fees
+
previously owed amounts
```

---

# 8. Fee Accounting Connection

The complete fee flow is:

```text
Swap
 ↓
feeGrowthGlobal
 ↓
feeGrowthOutside
 ↓
feeGrowthInside
 ↓
Position fee accounting
 ↓
tokensOwed
```

Then:

```text
tokensOwed
 ↓
collect()
 ↓
ERC20 transfer
```

---

# 9. `collect()`

`collect()` does **not remove liquidity**.

It withdraws tokens already owed to the position.

```text
tokensOwed
    ↓
collect()
    ↓
ERC20 transfer
```

It prevents withdrawing more than owed:

```text
actual amount
=
min(requested amount, tokensOwed)
```

After collection:

```text
tokensOwed -= collected amount
```

This prevents the same amount from being collected again.

---

# 10. `burn(0)`

You can call:

```solidity
burn(lowerTick, upperTick, 0);
```

This means:

```text
remove 0 liquidity
```

Therefore:

```text
liquidity → unchanged
```

But position accounting can still be updated, allowing newly accumulated fees to become recognized.

```text
burn(0)
   ↓
update position accounting
   ↓
recognize earned fees
   ↓
collect()
```

So:

> `burn(0)` does not create free money. It only updates accounting for fees already earned.

# 11. Most Important Mental Model

```text
SWAP
 ↓
uses active liquidity
 ↓
token composition can change
 ↓
fees accumulate
 ↓
liquidity normally remains

BURN
 ↓
removes liquidity
 ↓
calculates token0/token1 amounts
 ↓
adds amounts to tokensOwed

COLLECT
 ↓
checks tokensOwed
 ↓
decreases tokensOwed
 ↓
transfers actual ERC20 tokens
```

### One-line revision

> **Swap uses liquidity and earns fees; `burn()` removes liquidity and converts the removed liquidity into token amounts owed; `collect()` actually transfers those owed tokens. `burn(0)` updates fee accounting without removing liquidity.**
