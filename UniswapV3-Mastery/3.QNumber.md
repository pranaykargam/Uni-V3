# 1. Why Do We Need Q Numbers?⭐️

Solidity's standard integer types, such as `uint256`, do not directly support floating-point arithmetic.

For example:

```solidity
uint256 result = 5 / 2;

// result = 2
```

The fractional part is discarded.

But DeFi protocols frequently need fractional values for:

- Token prices
- Interest rates
- Exchange rates
- Liquidity calculations
- Collateral ratios
- Square-root prices

For example, a token price could be:

```text
1 ETH = 2500.50 USDC
```

An integer cannot directly represent `2500.50`.

**Solution:** Store the fractional value as a scaled integer.

This is the basic idea behind fixed-point arithmetic.

---

# 2. What Is Fixed-Point Arithmetic?⭐️

Fixed-point arithmetic represents a fractional number using an integer and a predefined scaling factor.

The general formula is:

```text
Encoded Value = Actual Value × Scaling Factor
```

To recover the represented value:

```text
Actual Value = Encoded Value ÷ Scaling Factor
```

### Example

Suppose we want to represent `2.5`.

Choose a scaling factor of `100`.

```text
Actual value = 2.5

Encoded value = 2.5 × 100

Encoded value = 250
```

The contract stores:

```solidity
uint256 encodedValue = 250;
```

To interpret the value:

```text
250 ÷ 100 = 2.5
```

The contract stores an integer, but we interpret that integer as a fractional value using the agreed scaling factor.

### Visual flowchart

```text
        Actual fractional value
                  |
                  v
       Multiply by scaling factor
                  |
                  v
          Encoded integer
                  |
           Stored in Solidity
                  |
                  v
        Divide by scaling factor
                  |
                  v
       Represented actual value
```

**Important:** The integer does not contain an explicit decimal point. The scaling factor tells us how to interpret it.

# 3. What Are Q Numbers?⭐️

Q numbers are a fixed-point representation that uses powers of two as scaling factors.

A common notation is:

```text
Qm.n
```

For these notes:

- `m` = number of integer bits
- `n` = number of fractional bits
- Scaling factor = `2ⁿ`

For example:

```text
Q8.4
```

This means:

```text
Integer bits    = 8
Fractional bits = 4

Total bits      = 12
Scaling factor  = 2⁴ = 16
```

Therefore:

```text
Actual value = Encoded value ÷ 16
```

### Example: Representing 2.5

```text
Actual value = 2.5
Scaling factor = 16

Encoded value = 2.5 × 16
              = 40
```

The integer `40` is the stored representation of `2.5` in this format.

Its binary representation, padded to 12 bits, is:

```text
000000101000
```

Split the bits into the integer and fractional portions:

```text
00000010 . 1000
 Integer   Fraction
```

The integer portion represents `2`, while the fractional portion represents:

```text
1000₂ = 8

Fraction = 8 ÷ 16
         = 0.5
```

Therefore:

```text
2 + 0.5 = 2.5
```

### Remember

```text
Q8.4
  |
  v
4 fractional bits
  |
  v
Scaling factor = 2⁴ = 16
  |
  v
2.5 × 16 = 40
  |
  v
Decode: 40 ÷ 16 = 2.5
```

---

# 4. Understanding Qm.n ⭐️

The number of fractional bits determines the scaling factor.

| Format | Fractional bits | Scaling factor |
|---|---:|---:|
| Q8.4 | 4 | 2⁴ = 16 |
| Q16.8 | 8 | 2⁸ = 256 |
| Q32.32 | 32 | 2³² |
| Q64.64 | 64 | 2⁶⁴ |
| Q64.96 | 96 | 2⁹⁶ |

The more fractional bits a format has, the finer its representable fractional precision can be.

However, the total bit width also matters. It affects the representable range and the size of arithmetic intermediates.

### Audit perspective

When you see a value in a smart contract, ask:

1. Is it an ordinary integer or a scaled integer?
2. What fixed-point format does the contract expect?
3. Which scaling factor must be used?
4. Does the variable have enough bits for the value?
5. Can an operation overflow or discard meaningful precision?

Never assume that two integers represent values in the same format simply because they have similar names.

# 5. Understanding Q64.96 ⭐️

Uniswap V3 uses a variable named:

```solidity
uint160 sqrtPriceX96;
```

This represents the pool's square-root price using a scaling factor of `2⁹⁶`.

The conceptual formula is:

```text
sqrtPriceX96 = √P × 2⁹⁶
```

Where:

- `P` is the raw token1/token0 price.
- `√P` is its square root.
- `2⁹⁶` is the scaling factor.

To recover the normalized square-root price:

```text
√P = sqrtPriceX96 ÷ 2⁹⁶
```

To recover the raw price:

```text
P = (sqrtPriceX96 ÷ 2⁹⁶)²
```

### Visual flowchart

```text
        Actual square-root price
                  |
                  v
             Multiply by
                2⁹⁶
                  |
                  v
           sqrtPriceX96
           Stored as uint160
                  |
                  v
              Divide by
                2⁹⁶
                  |
                  v
       Normalized square-root price
                  |
                  v
                Square
                  |
                  v
            Raw token price
```

### Why `uint160`?

The encoded value is stored in a 160-bit unsigned integer.

The Q64.96 name describes the fixed-point interpretation: 64 integer bits and 96 fractional bits.

```text
64 + 96 = 160 bits
```

This is the conceptual representation used for `sqrtPriceX96`.

**Important:** `sqrtPriceX96` represents a square-root price, not the ordinary price itself.

You must normalize it and square it to recover the raw price ratio.

# 6. Encoding and Decoding Q Numbers ⭐️

## 6.1 Encoding

Encoding means converting an actual value into its scaled integer representation.

For Q64.64:

```text
Encoded value = Actual value × 2⁶⁴
```

For example:

```text
Actual value = 2

Encoded value = 2 × 2⁶⁴
```

In Solidity, multiplying by a power of two can often be expressed using a left shift.

```solidity
uint256 encoded = uint256(2) << 64;
```

This is equivalent to multiplying `2` by `2⁶⁴`, provided the operation fits in the integer type.

## 6.2 Decoding

Decoding means recovering the represented value from the encoded integer.

```text
Actual value = Encoded value ÷ 2⁶⁴
```

For example:

```solidity
uint256 encoded = uint256(2) << 64;

uint256 decoded = encoded >> 64;

// decoded = 2
```

This example works because the encoded value represents an integer.

If the represented value has a fractional component, a right shift discards that fractional information rather than returning a decimal number.

### Left shift vs. right shift

| Operation | Meaning |
|---|---|
| `x << n` | Shifts bits left; equivalent to multiplying by `2ⁿ` when the result fits |
| `x >> n` | Shifts bits right; for unsigned integers, equivalent to floor division by `2ⁿ` |

### Audit warning

Shifts do not automatically protect against overflow.

Before using them, consider:

- The type width
- Whether significant bits are discarded
- Whether the result fits the destination type
- Whether the shift is being used with the correct scaling factor

# 7. How Do Multiplication and Division Work with Q Numbers? ⭐️

This is particularly important when reading DeFi math libraries.

## 7.1 Q-number multiplication

Suppose two Q64.64 values represent:

```text
A = 2.0
B = 3.0
```

Their encoded representations are:

```text
A = 2 × 2⁶⁴

B = 3 × 2⁶⁴
```

If we multiply the encoded integers directly:

```text
A × B
= (2 × 2⁶⁴) × (3 × 2⁶⁴)
= 6 × 2¹²⁸
```

But the result should remain encoded in Q64.64, which uses a scaling factor of `2⁶⁴`.

Therefore, divide the product by `2⁶⁴`:

```text
Encoded result = (A × B) ÷ 2⁶⁴
               = 6 × 2⁶⁴
```

The resulting encoded value represents:

```text
6.0
```

### Solidity example

```solidity
function multiplyQ64x64(
    uint128 a,
    uint128 b
) public pure returns (uint128) {
    uint256 product = uint256(a) * uint256(b);

    return uint128(product >> 64);
}
```

The right shift restores the expected scaling.

**Audit consideration:** The final `uint128` conversion can truncate high bits if the shifted result exceeds the type's range. The implementation must ensure the result fits.

## 7.2 Q-number division

Division requires the opposite adjustment: scale the numerator before dividing.

Suppose:

```text
A = 6.0
B = 2.0
```

We want:

```text
A ÷ B = 3.0
```

Let `A` and `B` be their Q64.64 encoded integers:

```text
A = 6 × 2⁶⁴
B = 2 × 2⁶⁴
```

If we divide them directly:

```text
A ÷ B
= (6 × 2⁶⁴) ÷ (2 × 2⁶⁴)
= 3
```

The result is the ordinary integer `3`, not the Q64.64 encoding of `3.0`.

To preserve the fixed-point scale, calculate:

```text
Encoded result = (A × 2⁶⁴) ÷ B
```

Substituting the encoded values:

```text
Encoded result
= (6 × 2⁶⁴ × 2⁶⁴) ÷ (2 × 2⁶⁴)
= 3 × 2⁶⁴
```

The result correctly represents `3.0` in Q64.64.

### General memory rule

```text
ADDITION / SUBTRACTION
        |
        v
Use compatible scaling factors

MULTIPLICATION
        |
        v
Multiply encoded values
        |
        v
Correct the scaling afterward

DIVISION
        |
        v
Scale the numerator first
        |
        v
Divide by the encoded denominator
```

These are conceptual formulas. Real Solidity implementations must also handle integer widths, intermediate overflow, division by zero, and truncation.

# 8. Why Use Powers of 2 Instead of Powers of 10? ⭐️

Solidity contracts frequently use decimal scaling conventions such as `1e18`.

For example, in a WAD-style representation:

```text
1.0 = 1e18

0.5 = 5e17
```

Q numbers use powers of two instead.

For Q64.64:

```text
1.0 = 2⁶⁴

0.5 = 2⁶³
```

Powers of two are convenient for binary arithmetic because multiplication and division by powers of two can often be implemented using bit shifts.

| Operation | Equivalent |
|---|---|
| `x << n` | `x × 2ⁿ`, if the result fits |
| `x >> n` | Integer division by `2ⁿ` for unsigned integers |

However, this does **not** mean every Q-number calculation is automatically cheaper or safer. Developers must still account for:

- Integer widths
- Intermediate overflow
- Truncation
- Precision loss
- Correct scaling
- Type conversions

### Quick comparison

| Feature | Decimal scaling (WAD) | Binary scaling (Q numbers) |
|---|---|---|
| Example scale | `1e18` | `2ⁿ` |
| Common use | Token amounts, rates, protocol math | Binary fixed-point calculations |
| Fraction representation | Integer scaled by a power of 10 | Integer scaled by a power of 2 |
| Main audit concern | Incorrect scale or rounding | Incorrect scale, shifts, overflow, or rounding |

# 9. Applying Q Numbers to Uniswap V3 ⭐️

You previously tested this value:

```solidity
uint160 sqrtPriceX96 =
    1629469382397940298438175600676214;
```

You passed it to:

```solidity
int24 tick =
    TickMath.getTickAtSqrtRatio(sqrtPriceX96);
```

Your test returned:

```text
tick = 198638
```

This connects the fixed-point representation to Uniswap V3's price and tick calculations.

## 9.1 Understand the price calculation

The value `sqrtPriceX96` is not an ordinary decimal square-root price.

It is the square-root price encoded using Q64.96 scaling.

Normalize it:

```text
Normalized √P = sqrtPriceX96 ÷ 2⁹⁶
```

Then square the normalized value:

```text
Raw P = (sqrtPriceX96 ÷ 2⁹⁶)²
```

For your example:

```text
sqrtPriceX96
      |
      v
Divide by 2⁹⁶
      |
      v
Normalized square-root price
      |
      v
Square the result
      |
      v
Raw token1/token0 price
```

The raw price is expressed in the ratio of the tokens' smallest units.

To convert it into a human-readable price, account for both tokens' decimals.

If token0 has `d0` decimals and token1 has `d1` decimals:

```text
Human token1 per token0 price
= Raw P × 10^(d0 - d1)
```

This formula assumes `P` is the raw token1/token0 ratio. To obtain the opposite price direction, take the reciprocal of the correctly normalized price.

**Audit warning:** Incorrect token decimal adjustments or reversed price direction can cause a price calculation to be wrong even when the fixed-point arithmetic itself is correct.

## 9.2 What does `TickMath` do?

The function:

```solidity
TickMath.getTickAtSqrtRatio(sqrtPriceX96)
```

accepts the encoded square-root price and returns the greatest tick whose corresponding square-root ratio is less than or equal to the supplied ratio, within the function's supported range.

Remember:

- `sqrtPriceX96` represents the current square-root price.
- A tick represents a discrete price boundary.
- The exact current price and the tick are related, but they are not interchangeable.
- `TickMath` expects the encoded representation, not a decoded decimal square-root price.

# 10. Audit Checklist ⭐️

When reviewing a contract that uses fixed-point arithmetic, ask the following questions.

### A. Scaling

- Is the scaling factor correct?
- Is the value being interpreted in the expected fixed-point format?
- Are two values using compatible scales before addition or subtraction?
- Is a decoded value accidentally passed to a function that expects an encoded value?

### B. Multiplication and division

- Does multiplication correct the scaling afterward?
- Does division scale the numerator before dividing?
- Can integer division discard meaningful precision?
- Can division by zero occur?

### C. Overflow and truncation

- Can an intermediate multiplication overflow?
- Is the chosen integer width sufficient?
- Can a cast to a smaller type truncate high bits?
- Does a shift discard significant bits?
- Is the result bounded before conversion?

### D. Uniswap V3 price calculations

- Is `sqrtPriceX96` normalized using `2⁹⁶`?
- Is the normalized square-root price squared when calculating the raw price?
- Are token decimals handled correctly?
- Is the token0/token1 direction correct?
- Is `TickMath` receiving the expected encoded value?
- Are calculations using safe intermediate arithmetic where necessary?

### Audit workflow

```text
Read the Solidity function
          |
          v
Identify encoded values
          |
          v
Find their scaling factors
          |
          v
Trace multiplication / division
          |
          v
Check integer widths and casts
          |
          v
Check rounding and precision loss
          |
          v
Verify token decimals and price direction
          |
          v
Test boundary cases with Foundry
```

### Foundry test ideas

For functions that perform fixed-point calculations, consider testing:

1. Zero and minimum valid inputs.
2. Values near the maximum permitted range.
3. Inputs that cause nonzero fractional remainders.
4. Multiplication near the intermediate type's limit.
5. Conversion to a smaller integer type.
6. Division by zero, where the input is not already rejected.
7. Token pairs with different decimal counts.
8. Prices near supported tick boundaries.

These are test ideas, not proof that a vulnerability exists. Verify the expected behavior against the function's specification and surrounding code.
