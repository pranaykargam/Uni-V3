

## 1. Why Do We Need Q Numbers?⭐️

Solidity's standard integer types, such as `uint256`, do not support floating-point arithmetic.

For example:

```solidity
uint256 result = 5 / 2;

// result = 2, not 2.5
```

Integer division truncates the fractional part.

However, DeFi protocols need fractional values for:
- Token prices: `0.5`
- Interest rates: `0.025`
- Exchange ratios: `1.25`
- Square-root prices in Uniswap V3

**Solution:** Fixed-point arithmetic represents fractional values using integers and a predefined scaling factor.

## 2. What Is a Fixed-Point Number?⭐️

A fixed-point number represents a value using an integer and a scaling factor.

Suppose the scaling factor is `1000`.

**Encoding:**

```text
Actual value × Scaling factor = Stored integer

2.5 × 1000 = 2500
```

**Decoding:**

```text
Stored integer / Scaling factor = Actual value

2500 / 1000 = 2.5
```

| Actual value | Stored integer | Scaling factor |
|---:|---:|---:|
| 1.0 | 1000 | 1000 |
| 0.5 | 500 | 1000 |
| 2.5 | 2500 | 1000 |
| 0.125 | 125 | 1000 |

The computer stores the integer. The program must know the scaling convention to interpret it correctly.

**Key takeaway:** A stored integer does not automatically represent the same numerical value as the original number.

---

## 3. What Is a Q Number?⭐️

A Q number is a fixed-point representation that uses a power of two as its scaling factor.

The scaling factor is determined by the number of fractional bits.

For example, in Q8.4:

```text
Integer bits    = 8
Fractional bits = 4
Scaling factor  = 2⁴ = 16
```

To represent `2.5`:

**Encoding:**

```text
2.5 × 16 = 40
```

**Decoding:**

```text
40 / 16 = 2.5
```

The computer stores `40`, but when interpreted using the Q8.4 scaling convention, it represents `2.5`.

### Remember

- Q numbers use powers of **2** for scaling.
- Decimal fixed-point conventions may use powers of **10**.
- The scaling factor determines how the stored integer is interpreted.

## 4. Understand Qm.n Notation⭐️

Consider Q8.4.

| Component | Meaning |
|---|---|
| Q | Fixed-point representation |
| `m = 8` | Integer bits |
| `n = 4` | Fractional bits |
| Total | 12 bits |
| Scaling factor | `2⁴ = 16` |

### Example: Representing 2.5

First, encode the value:

```text
2.5 × 16 = 40
```

The integer `40` in binary is:

```text
101000
```

Padded to 12 bits:

```text
000000101000
```

Interpreted as Q8.4, the binary point is placed after the first eight bits:

```text
00000010.1000
Integer  Fraction
```

The integer portion represents `2`.

The fractional portion is:

```text
1000 = 1/2 = 0.5
```

Therefore:

```text
2 + 0.5 = 2.5
```

### Why Do Integer and Fractional Bits Matter?

- **More integer bits:** Allow a larger representable range.
- **More fractional bits:** Allow finer fractional precision, generally at the cost of integer range when the total bit width is fixed.

For example, Q8.4 and Q4.8 both use 12 bits, but Q4.8 allocates more bits to fractional precision.

## 5. What Does Q64.96 Mean in Uniswap V3?⭐️

Uniswap V3 stores the pool's square-root price in:

```solidity
uint160 sqrtPriceX96;
```

The `X96` indicates that the square-root price is scaled by `2⁹⁶`.

Conceptually:

```text
sqrtPriceX96 = √P × 2⁹⁶
```

Here, `P` is the raw token1/token0 price, with token amounts expressed in their smallest units.

### Recover the Square-Root Price

Divide the stored value by the scaling factor:

\[
\sqrt{P}=\frac{\text{sqrtPriceX96}}{2^{96}}
\]

### Recover the Raw Price

Square the normalized square-root price:

\[
P=\left(\frac{\text{sqrtPriceX96}}{2^{96}}\right)^2
\]

**Important:** The normalized square-root price is not the actual price. You must square it to obtain the raw price.

### Example: When the Price Is 1

If:

\[
P=1
\]

Then:

\[
\sqrt{P}=1
\]

Therefore:



In Solidity:

```solidity
uint160 encodedOne = uint160(1) << 96;
```

The resulting integer is:

```text
79228162514264337593543950336
```

Although this integer is enormous, it represents the square-root price `1` under Q64.96 scaling.

### Why `uint160`?

Q64.96 conceptually allocates:

```text
64 integer bits + 96 fractional bits = 160 bits
```

This explains the relationship between the format and the `uint160` storage type.

### Raw Price vs. Human-Readable Price

The formula produces the raw token1/token0 ratio.

To obtain a human-readable price, account for:
- Token0 decimals.
- Token1 decimals.
- The direction of the price ratio.

Do not assume the raw price directly equals the exchange rate displayed by a frontend.

## 6. Convert Between Integers and Q Numbers⭐️

There are two fundamental operations.

### A. Encoding: Value → Q Representation

Multiply the value by the scaling factor.

For Q64.96:


In Solidity, a left shift by 96 bits is equivalent to multiplying an unsigned integer by `2⁹⁶`, provided the result fits the selected type.

```solidity
uint256 encoded = uint256(5) << 96;
```

Conceptually:

```text
5
↓
Multiply by 2⁹⁶
↓
Q64.96 encoded representation
```

### B. Decoding: Q Representation → Value

Divide the encoded integer by the scaling factor.

For example:

A right shift can extract the integer portion:

```solidity
uint256 integerPart = encoded >> 96;
```

However, **right-shifting discards the fractional bits**. It does not preserve the complete fractional value.

When precise fractional arithmetic is required, use an appropriate fixed-point calculation or a sufficiently precise off-chain numeric representation.

### Quick Reference

| Operation | Meaning |
|---|---|
| `x << n` | Multiply an unsigned integer by `2ⁿ`, subject to type-width limits |
| `x >> n` | Shift right; for unsigned integers, equivalent to floor division by `2ⁿ` |
| Encode | Multiply by the scaling factor |
| Decode | Divide by the scaling factor |
| Recover raw price | Square the normalized square-root price |

## 🔍 Uniswap V3 Auditing Perspective

These six sections establish the foundation for auditing fixed-point calculations.

When reviewing Uniswap V3 contracts, ask:

**1. Is the scaling factor correct?**

Check whether a value uses `2⁹⁶`, `1e18`, or another scaling convention. Mixing conventions can produce incorrect results.

**2. Is the square-root price interpreted correctly?**

Confirm that `sqrtPriceX96` is normalized before treating it as a real square-root price, and squared when calculating the raw price.

**3. Can precision be lost?**

Solidity integer division truncates fractional results. Check whether the order of multiplication and division causes meaningful rounding errors.

**4. Can intermediate calculations overflow?**

A multiplication can overflow even when the final mathematical result would fit. Inspect integer widths, casts, and intermediate arithmetic.

**5. Are token decimals handled correctly?**

A correct raw token1/token0 ratio can still produce an incorrect human-readable price if decimal adjustments or price direction are wrong.

### Audit Workflow

When you encounter an unfamiliar price calculation:

```text
Identify the stored value
        ↓
Identify its scaling factor
        ↓
Determine whether it is a price or square-root price
        ↓
Trace multiplication, division, and rounding
        ↓
Check overflow and integer-width assumptions
        ↓
Verify token decimals and price direction
```

**Audit principle:** Never assume that a large integer is an actual price. First establish how the protocol encodes and interprets it.
