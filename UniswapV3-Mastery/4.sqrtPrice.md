# 🧭 `sqrtPriceX96` — Read the Pool Like an Auditor

> **Mission:** Look at one number from a Uniswap V3 pool and work out what the market is telling you — without getting tricked by scaling, token order, or Solidity integer math.

This is a practical field note: build the mental model, decode the number, then learn where it can fool you during an audit.

---

## 0. The 10-second mental model

Imagine the pool has a tiny dashboard:

```solidity
(uint160 sqrtPriceX96, int24 tick, , , , , ) = pool.slot0();
```

`sqrtPriceX96` is the pool’s current price, but encoded in a form that makes liquidity math efficient.

Three things to remember:

- **`sqrt`** — the stored value represents the *square root* of price.
- **`X96`** — the number is scaled by \(2^{96}\), so Solidity can represent a fractional value using integers.
- **`price`** — after decoding, it means **token1 raw units per token0 raw unit**. Token order matters.

If those three ideas stay in your head, the rest becomes a decoding exercise.

---

## 1. Why store the square root? 🌗

A swap changes the pool price. Uniswap V3 constantly needs to calculate how token amounts and liquidity relate to that price.

The key relationship is:

\[
P = \left(\frac{y}{x}\right)^2
\qquad\text{and}\qquad
S = \sqrt{P}
\]

Here:

- \(P\) is the raw `token1/token0` price.
- \(S\) is its square root.
- The pool stores \(S\), not the human-readable price \(P\).

The square-root form fits the concentrated-liquidity equations used during swaps and liquidity changes.

**Think of it this way:** price is the destination; `sqrtPriceX96` is the coordinate system the engine uses to get there.

---

## 2. Decode the number 🔓

Uniswap uses a **Q64.96** fixed-point representation.

That means the stored integer is scaled by:

\[
Q96 = 2^{96}
\]

So:

\[
S = \frac{\texttt{sqrtPriceX96}}{2^{96}}
\]

And the raw price is:

\[
P_{\text{raw}} = S^2
= \frac{\texttt{sqrtPriceX96}^2}{2^{192}}
\]

### Decoding recipe

1. Read `sqrtPriceX96` from `slot0()`.
2. Divide by \(2^{96}\) to understand the square-root price conceptually.
3. Square it to get the raw `token1/token0` price.
4. Adjust for token decimals before calling it a human price.

> ⚠️ **Solidity reality check:** do not blindly implement the formula as:
>
> ```solidity
> sqrtPriceX96 * sqrtPriceX96 / 2 ** 192
> ```
>
> The intermediate square may overflow `uint256`. Production code needs full-precision arithmetic and carefully chosen operation order.

---

## 3. Raw price is not human price 🪙

This is where otherwise-good integrations go wrong.

The decoded ratio uses the tokens’ **smallest units**. An 18-decimal token and a 6-decimal token do not use the same unit scale.

Let:

- `d0` = decimals of `token0`
- `d1` = decimals of `token1`
- `P_raw` = raw token1 units per raw token0 unit

Then:

\[
P_{\text{human, token1 per token0}}
= P_{\text{raw}} \times 10^{d0-d1}
\]

### Tiny example

Suppose:

- `token0` has 18 decimals
- `token1` has 6 decimals
- The decoded raw ratio is:

\[
P_{\text{raw}} = 0.000000002
\]

Then:

\[
P_{\text{human}} = 0.000000002 \times 10^{18-6}
= 2{,}000
\]

That reads as **2,000 token1 per token0**.

> The math above is only an example of decimal conversion. In a real pool, confirm token ordering and verify the result against a trusted quote.

### Before trusting a price, ask

- Is this token actually `token0` or `token1`?
- Am I quoting `token1 per token0`, or the inverse?
- Have I adjusted for both tokens’ decimals?
- Does the displayed price agree with a known pool quote?

---

## 4. The tick is a nearby landmark, not the same number 📍

Uniswap V3 also exposes `tick` in `slot0()`.

Each tick represents a price step based on:

\[
P_{\text{tick}} = 1.0001^{\text{tick}}
\]

A useful mental picture:

| Value | Meaning |
|---|---|
| `sqrtPriceX96` | The more precise current position |
| `tick` | The grid location used by the protocol’s tick system |

Do **not** assume that converting a tick back to a square-root ratio will always reproduce the exact stored `sqrtPriceX96`.

Tick boundaries, rounding, and the current position within a tick matter.

## 5. Follow the number into the code 🕵️

Start with the pool, then follow the math libraries. This is a better learning path than memorizing formulas in isolation.

| File | What to investigate |
|---|---|

| `TickMath.sol` | Tick ↔ square-root-price conversion and valid bounds |
| `SqrtPriceMath.sol` | How token amounts and liquidity change with square-root price |
| `SwapMath.sol` | How a swap moves price toward its next target |
| `FullMath.sol` | Full-precision multiplication and division |

| `Oracle.sol` | Tick-based observations and time-weighted data |

**Repository:** [Uniswap V3 Core](https://github.com/Uniswap/v3-core)

### Code-reading route

```text
UniswapV3Pool.slot0
        ↓

        ↓

        ↓

        ↓

```

Use this as a map, not as a claim that every swap follows one single straight-line call path.

## 6. Auditor mode: where can this number betray you? 🚨

When reviewing a price calculation, trace the complete path:

```text
SOURCE → TOKEN ORDER → SCALE → MATH → ROUNDING → CONSUMER
```

Look for these failure patterns:

- **Wrong direction:** the code treats `token0/token1` as if their order were fixed.
- **Missing decimals:** a raw-unit ratio is displayed or used as a human-unit price.
- **Scale dropped:** the code divides by `Q96` or `Q192` at the wrong stage.
- **Overflow:** multiplication happens before a safe full-precision division.
- **Unsafe cast:** a wide value is narrowed without proving it fits.
- **Bad bounds:** invalid ticks or square-root prices are accepted.
- **Rounding mismatch:** one side rounds down when the protocol’s safety logic expects rounding up, or vice versa.
- **Spot price used as truth:** a consumer uses the current pool price as an oracle without considering manipulation and time-weighting.
- **Wrong assumption about tick:** code assumes the tick alone fully describes the exact current price.

### Useful audit question

> If an attacker can influence this pool’s spot price for a short time, can this value affect collateral, minting, liquidation, or a payout before the price is checked safely?

A correct formula does not automatically make a safe oracle.

---

## 8. Keep these five rules in your pocket 🧠

1. `sqrtPriceX96` is a scaled square-root price, not a normal price.
2. `Q96 = 2^96`; square the decoded value to get the raw ratio.
3. The raw ratio is `token1 per token0` — verify token ordering.
4. Token decimals change the human-readable result.
5. For audits, inspect precision, rounding, bounds, and how the price is consumed.
